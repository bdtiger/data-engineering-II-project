\section{System Architecture}

The system consists of two interconnected pipelines: a \textbf{data collection pipeline} that
crawls the GitHub API and produces a training dataset, and a \textbf{prediction pipeline} that
trains, evaluates, and deploys machine learning models. Both pipelines run on infrastructure
provisioned via OpenStack on the SNIC Science Cloud and configured with Ansible.

\subsection{Infrastructure and Orchestration}

Two virtual machines are used throughout the project. A \textbf{Client VM} acts as the Ansible
controller and OpenStack operator: it provisions the Dev and Prod VMs using a Python script
(\texttt{start\_instances.py}) that calls the OpenStack API, and subsequently configures them
using Ansible playbooks. All application components run inside Docker containers orchestrated
with Docker Compose.

The \textbf{Dev VM} hosts the data collection scripts and the model training pipeline. The
\textbf{Prod VM} hosts the live prediction service, consisting of a Flask web application, a
Celery task queue, and a Redis message broker. A bare Git repository on the Dev VM, equipped
with a \texttt{post-receive} Git Hook, automates model deployment: a single \texttt{git push}
from the Dev VM copies the best model artifact to the Prod VM and restarts the production
containers.

\subsection{Data Collection Pipeline}

\begin{figure}[h]
  \centering
  \includegraphics[width=0.82\linewidth]{figures/diagram1_data_collection_pipeline.jpg}
  \caption{Data collection pipeline running on the Dev VM.}
  \label{fig:data-pipeline}

The crawler (\texttt{collect\_github.py}) queries the GitHub Search API for repositories with at
least 50 stars, sorted by star count in descending order, using pagination to collect 1{,}000
repositories in total. A two-second delay between requests ensures compliance with the GitHub
API rate limits. For each repository, 14 features are extracted directly from the API response,
as listed in Table~\ref{tab:features}. Star counts are log-transformed ($\log(1 + \text{stars})$)
before training to stabilise variance across the wide range of values observed in the dataset.

\begin{table}[h]
  \centering
  \small
  \begin{tabular}{ll}
    \toprule
    \textbf{Feature} & \textbf{Description} \\
    \midrule
    \texttt{forks}             & Number of repository forks \\
    \texttt{watchers}          & Number of watchers \\
    \texttt{open\_issues}      & Count of open issues \\
    \texttt{size\_kb}          & Repository size in kilobytes \\
    \texttt{has\_wiki}         & Binary: wiki enabled \\
    \texttt{has\_projects}     & Binary: projects enabled \\
    \texttt{has\_downloads}    & Binary: downloads enabled \\
    \texttt{is\_fork}          & Binary: is a fork \\
    \texttt{age\_days}         & Days since repository creation \\
    \texttt{days\_since\_push} & Days since last commit push \\
    \texttt{topics\_count}     & Number of topics assigned \\

\subsection{Prediction Pipeline and CI/CD}

\begin{figure}[h]
  \centering
  \includegraphics[width=0.82\linewidth]{figures/diagram2_prediction_app_cicd.jpg}
  \caption{Prediction pipeline and automated deployment via Git Hook.}
  \label{fig:cicd-pipeline}
\end{figure}

Five regression models are trained on the Dev VM using an 80/20 train--test split:
Linear Regression, Ridge Regression ($\alpha = 1.0$), Random Forest (200 estimators),
Gradient Boosting (200 estimators), and SVR (RBF kernel). Each model is wrapped in a
scikit-learn \texttt{Pipeline} that applies \texttt{StandardScaler} before the estimator.
All models are evaluated using $R^2$ on the held-out test set. The best-performing model
is saved as \texttt{best\_model.pkl}.

Deployment is fully automated via a Git Hook. After training, the developer commits
\texttt{best\_model.pkl} and pushes to a bare repository on the Dev VM. The
\texttt{post-receive} hook securely copies the model file to the Prod VM via SCP and
restarts the Docker containers. No manual steps are required on the production server.

On the Prod VM, the Flask application exposes a \texttt{/predict} endpoint that accepts
a JSON list of repository feature vectors. Prediction tasks are dispatched asynchronously
to Celery workers backed by Redis, and results are polled via a \texttt{/result/<task\_id>}
endpoint. This design allows the serving layer to handle concurrent requests without blocking.

\subsection{Combined System Overview}

\begin{figure}[h]

Figure~\ref{fig:combined} presents the end-to-end architecture. The Client VM provisions
and configures all infrastructure. The Dev VM handles data-intensive work and model
development. The Prod VM exposes the prediction service to end users. The Git Hook
bridges the two application VMs, making the entire CI/CD cycle reproducible with a
single command.
